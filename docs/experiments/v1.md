# V1：RV32IM 单发射乱序 CPU

2026 年 10 月 15 日实现。此版本建立完整的功能与验证基线；尚未达到课程性能档的 IPC 和频率要求。整体规划见 [arch.md](../arch.md)，本机工具使用见 [local-environment.md](../local-environment.md)。

## 实现范围

| 部分 | V1 行为 |
| --- | --- |
| ISA | 全部课程要求的 RV32I 与 8 条 M 扩展指令 |
| 重命名 | 32 项 RAT/RRAT，48 项 PRF，空闲位图；x0 固定映射与数值 |
| 调度 | 16 项 ROB、8 项 IQ，每周期从就绪候选中选最老的一条，可越过未就绪老指令 |
| 提交 | 每周期按序提交一条；Store 在 ROB 头发送，等待写响应与 Cache 更新完成 |
| 乘除 | 32 步迭代，执行期间其他指令可发射；完成结果可等待写回 |
| 写回 | Load、MDU、普通运算共享一个 PRF 写口，按该顺序仲裁 |
| 恢复 | 默认预测 PC+4；误预测分支到 ROB 头后恢复 RAT、回收推测寄存器、清空年轻指令 |
| 访存 | 逻辑 LSQ 容量 8，元数据放在 ROB；Load 不越过更老 Store；最多一笔数据请求 |
| Cache | I/D 各 2 KiB，直接映射、16 B 行；数据使用框架同步 SRAM；D 写穿、写不分配 |
| AXI | 读通道公平仲裁、全局一笔在途读；逐字填充；AW/W 独立握手且负载保持稳定 |
| 故障 | 非法指令、非对齐、外存错误到达 ROB 头时诊断失败；错误路径故障可被清空 |

不实现 CSR、FENCE、特权异常处理、自修改代码、分支预测表、Store Buffer、访存转发或多发射。初始架构寄存器均为零，PC 为零，栈由程序初始化。

## 代码组织与关键约定

- `verilog/student_top.sv`：课程顶层、参数以及核心和存储系统连线。
- `verilog/cpu_core.sv`：前端单项缓冲、RAT/RRAT/PRF、ROB/IQ、保守 LSU、提交与恢复。状态统一由一个时序过程管理，避免同拍分配、回收和恢复相互覆盖。
- `verilog/execute/`：严格译码、ALU、迭代乘除。
- `verilog/memory/`：两个阻塞 Cache 及存储系统连接。
- `verilog/bus/axi_lite_bridge.sv`：读仲裁、响应归属、独立写握手。

本版本使用普通逻辑端口和字段数组，没有依赖复杂 package/interface。可综合代码不使用声明初始化或 `initial` 初始化硬件状态。非法参数在展开时拒绝；仿真诊断、断言和追踪均排除在综合之外。

取指和数据请求一旦被 Cache 接受就必须排空。核心在分支恢复时保留原事务上下文，使用 `fetch_drop` / `mem_killed` 丢弃迟到返回；在它返回前不复用对应的请求槽，因此没有有限世代号回绕问题。MDU 可直接同步取消。Cache 可以保留有效的错误路径读填充，但出错行不会安装。

顶层可配置 ROB/PRF/IQ/LSQ 容量、I/D Cache 容量、行大小。V1 的 `ISSUE_WIDTH`、`ICACHE_WAYS`、`DCACHE_WAYS` 仅支持 1；不能只修改这些参数就获得多发射或相联 Cache。容量配置和编译时参数记录在验证构建的 `build.json` 中。

## 日常运行

```sh
tools/dev mac build
tools/dev mac test SIM=build/macos/sim
tools/dev mac perf SIM=build/macos/sim LATENCY=10

tools/dev start
tools/dev linux build
tools/dev linux test SIM=build/linux/sim
tools/dev linux synth MODE=opt
```

`SIM` 复用已编译的模拟器；修改 RTL 后先重新 `build`。Mac 与 Linux 输出目录分开，官方脚本、Makefile、Dockerfile 和测试子模块内容未修改。课程 Linux Verilator 5.020 与 Mac Verilator 5.052 均已实际编译、运行。

完整功能回归使用 100,000,000 周期上限；其中 `correctness_pi` 实测 45,527,614 周期，因此默认 1,000,000 周期上限不足以运行这一版本的完整程序集。

## 提交轨迹与独立验证

```sh
verification/unit/run_execute.sh
verification/unit/run_memory_system.sh
python3 verification/directed/generate.py
python3 verification/runners/build_trace.py --jobs 6
python3 verification/runners/run_cpu.py \
  --sim build/verification/trace/sim --latencies 1,10,31
```

追踪构建默认 `TRACE=1`，使用官方模拟器源码，逐条比较独立 RV32IM 参考模型。普通课程构建默认 `TRACE=0`，不向 OJ 标准输出打印调试事件。带追踪的模拟器用于自建 runner，不用于官方 OJ 输出比较。

`DISPATCH` 的 id 是每次重命名分配的唯一调试序号，包含 PC、指令、架构及物理目标；`ISSUE`、`COMPLETE` 使用同一 id。`COMMIT` 另有连续的 seq，按架构顺序比对 PC、指令、寄存器值及 Store 字节效果。`FLUSH` 与 `DROP_LOAD` 用于检查取消和迟到响应。

Store 的 `COMMIT` 追踪在 ROB 头将不可撤销写交给 Cache 时产生，ROB 槽仍保留到 B 与本地更新完成；这是为了包含退出 MMIO，因为官方模拟器会在退出写的 B 握手时立即结束。该事件不会允许年轻指令越过 Store 退休，也不会在 Store 最终退队时重复打印。

执行单元测试包括 4,035 次译码检查、6,628 次 ALU 检查、2,257 次乘除运算，以及结果背压、取消和复位。存储测试覆盖 AW/W 不同先后、响应背压、公平仲裁、替换、部分字节写、填充错误、写错误、MMIO 和 SRAM 访问顺序。所有测试使用独立目录，未改变官方验证模型。

最终默认配置通过 **21 组 × 3 种延迟 = 63 次**回归，逐条比较 **55,602 次架构提交**，并强制检查真实乱序发射和错误路径覆盖。例如 `LATENCY=10` 的恢复测试中，错误 Load 在第 691 拍发射，第 692 拍被清空，其物理目标 p33 在第 702 拍已被正确路径重新分配，原响应直到第 767 拍才被安全丢弃。

另测 ROB=5、PRF=37、IQ=3、LSQ=3、I/D Cache 各 128 B、8 B 行的非 2 的幂队列配置：延迟 1/10 下 **42/42 通过，比较 37,068 次提交**。该配置关闭依赖特定窗口时序的 OoO/投机覆盖检查，仍完整进行逐提交比对。11 项参考模型及覆盖检查器单测通过；21 组机器码均与 GNU 汇编器独立编码一致；参考模型执行官方 25 个程序的结果和动态指令数也一致。

有效路径的非法指令、对齐错误、越界读写及越界取指另做负向验收，要求精确故障编号与 PC；Mac/Linux 各 **27/27 通过**：

```sh
python3 verification/runners/run_faults.py \
  --sim build/macos/sim --latencies 1,10,31
```

可复现的参数、RTL 校验值、逐项周期、综合测量和关键覆盖证据保存在 [v1-results.json](v1-results.json)。完整验证用法见 [验证说明](../../verification/directed/README.md)。

## 性能基线与下一步

默认 `LATENCY=10`，Mac 与 Linux 的周期数一致；19 个正确性程序和 6 个性能程序均返回正确结果。

| 性能程序 | 周期数 | IPC |
| --- | ---: | ---: |
| median | 59,734 | 0.1165 |
| multiply | 140,369 | 0.1547 |
| qsort | 1,238,315 | 0.1130 |
| rsort | 1,608,397 | 0.1217 |
| towers | 51,066 | 0.1034 |
| vvadd | 44,488 | 0.1017 |
| 几何平均 | — | **0.1173** |

课程 Yosys 0.63 + ASAP7 + OpenSTA 3.1.0、`MODE=opt`、目标周期 2 ns 的综合结果：总面积 **9,063.421 μm²**，其中 SRAM **1,375.941 μm²**；估算最高频率 **44.52 MHz**，最小周期 **22.4600 ns**，最差建立时间裕量 **−20.4596 ns**。这说明可综合，但时序没有收敛；2 ns 目标不等于已经达到 500 MHz。

下一版优先处理三处限制：

1. 取指只有一个请求和一个缓冲，Cache 命中也需要串行查询与交付，约每 5 拍才能供应一条指令。先流水化取指并增加队列，再优化发射吞吐。
2. 每条 Cache 行逐字等待外存，每次跳转到提交点才恢复。随后加入行内多笔在途读、分支预测和更早恢复。
3. 全局调度、PRF 选择和恢复组合逻辑集中且扇出大。结合时序报告分拆关键路径、降低扇出，并建立分阶段时序预算；不能只增加队列规模。

当前版本不能据此宣称达到 90/95/100 分性能档。它提供可回归的正确性起点和可测量的优化基线。
