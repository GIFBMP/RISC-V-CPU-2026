# V10 实验：参考 adder32 的对照（未采用）

参考用户提供的 `arch-hw3/adder32/answer.v`，在 [V10](v10.md) 基线上测试了三种改写。**三个候选均未达到 500 MHz，因此没有采用，生产 RTL 已恢复为 V10。** 恢复后的全部生产输入摘要与 [V10 验收](v10-results.json) 完全一致。本页是 V10 的失败候选记录，不产生 V11 发布版本；版本编号规则见 [文档索引](../README.md)。

当前 `address_adder` 本来就是跨度 1、2、4、8、16 的五层并行前缀加法器，参考文件也采用这一结构。此次主要比较传播位定义和向量表达方式，没有增加流水级或改变 CPU 的执行拍数。源码、工具、约束、逐提交结果、未采用补丁的摘要见 [实验 JSON](v10-adder-reference-results.json)。

## 为什么不能直接照搬

参考文件采用 `G=A&B`、`P=A^B`；当前实现采用 `G=A&B`、`P=A|B`。两者都满足 `carry_next = G | (P & carry)`：当 A、B 都为 1 时，G 已经强制产生进位，因此 OR 和 XOR 传播位在这个输入上的差异不改变进位结果。原版最终的和仍使用 `A ^ B ^ carry`。

两种传播定义都可以按以下规则合并相邻区间：

```text
G_new = G_high | (P_high & G_low)
P_new = P_high & P_low
```

参考文件把每层写成整条向量运算。合并跨度为 d 时，低端的 P 补 1、G 补 0，相当于保持低 d 位原值。这种写法可简化表达，但综合器会重新优化、共享和映射逻辑；数学等价、层数相同不保证最终完整 CPU 的时序相同。此处只能得出三个具体候选未通过约束，不能推广为 XOR 传播一定比 OR 传播慢。

前两个候选生成的 trace 仿真 C++ 源码由约 16.57 MB 缩至约 15.41 MB；第三个候选则增至约 17.45 MB。**代码体积不是运行速度证据。** 三个候选在时序门槛处淘汰，没有继续测量官方单线程 pi 耗时，也没有宣称任何提速。原版 pi 的 302.8770 秒 / 11,839,760 周期是上一轮本机课程容器实测，不是本轮重测或 OJ 服务器实测。

## 本轮实际执行的验证

每个候选分别通过：

| 检查 | 每个候选的结果 |

| 加法器对数学加法的全输入组合 SAT | 通过 |

| 六项性能程序逐提交对比 | 6/6，指令数和周期不变 |

SAT 覆盖组合逻辑的全部二态输入，不是完整 CPU 状态机的形式证明。定向测试保留逐提交比较、乱序和推测覆盖要求。现代宿主 Verilator 5.052 对第三个候选的原逐位求和表达式提示未命名 generate 分支；基线已有同样提示，排除该已有提示后无其他 lint 警告。

本轮没有为被淘汰候选重跑官方 19 项长程序、五组兼容配置和故障矩阵。原版完整正确性的证据仍是上一轮验收；已经核对恢复后的 RTL、官方脚本及配置摘要，不把历史执行描述成本轮重跑。
